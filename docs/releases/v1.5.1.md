# v1.5.1 - Audited consent across tabs

This patch fixes a race in **optional decision auditing**. A delayed acceptance receipt can no longer overwrite a newer saved refusal, partial selection, or withdrawal made in another tab. **Existing APIs and saved preferences remain compatible.**

## Fixed

- Pending audited choices now re-read **shared browser preferences** before applying a successful receipt. If another tab or a server response changed the saved decision, the older choice is discarded instead of restoring permission and starting scripts for denied categories.
- An external change already observed through refresh also invalidates the pending choice and its reload-recovery handoff. A later receipt cannot revive that choice, even if the cookie subsequently returns to its earlier value. Fresh explicit choices after an external change still work, and immediate refusal, withdrawal, and mixed-choice reload recovery retain their existing behavior.

## Upgrade

```bash
composer require "jakub-lipinski/consent-for-laravel:^1.5.1"
php artisan view:clear
```

Commit the application's Composer files and deploy with `composer install`. Preserve existing services, presets, policy version, cookie scopes, audit settings, and custom wording. Rebuild relevant deployment caches and restart long-running workers.

**No API changes, new configuration keys, database migrations, policy-version change, or consent reset are required.** The preference cookie schema, service fingerprints, and existing decision lifetimes remain compatible.

**Deploy the updated `consent.js`.** Inline components use the installed source; invalidate cached HTML containing the old runtime. If serving published assets, refresh/cache-bust `consent.js`, preserving application customizations and refreshing relevant asset/CDN caches. The banner markup, `banner.js`, CSS, and translations are unchanged from v1.5.0. Apply the relevant earlier upgrade steps when skipping releases.

A successful receipt does not guarantee that its requested choices became the current browser preferences. A superseded choice resolves with the current state; its already committed audit row remains in history. Custom controls must use the current permission when deciding whether to send measurements.

Refresh selected Boost resources with `php artisan boost:update`, preserving application overrides. The existing audit and verification references cover shared-cookie tabs and delayed receipts; no additional skill or reference is required.

See the [audit log guide](https://github.com/jakub-lipinski/consent-for-laravel/blob/v1.5.1/docs/audit-log.md), [Boost guide](https://github.com/jakub-lipinski/consent-for-laravel/blob/v1.5.1/docs/boost.md), and [upgrade sequence](https://consent.lipinskijakub.pl/docs/upgrading#cross-tab-audit-fix) for receipt behavior, deployment, and verification in the host application.

The new two-tab scenarios use actual signed notices, SQLite writes, and held committed receipts, checking both saved preferences and the absence of denied SDK requests or dependent script execution.
- The existing browser suites also checked navigation, component and interface language changes, history, persistence, active-withdrawal reload, modules, nonce CSP, keyboard/focus, reflow, and enlarged text. Documentation rendering, chapter links, the v1.5.1 landing link, and Boost resources passed their focused tests.
