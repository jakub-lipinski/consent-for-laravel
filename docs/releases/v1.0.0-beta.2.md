# v1.0.0-beta.2 - Consent-aware script lifecycle

This beta connects the PHP consent foundation to a browser runtime. Optional scripts remain inert until there is a current saved grant, then load in order without repeating their initialization. A decision can change on the same page. Withdrawing permission blocks queued scripts and normally reloads the document to stop already running code.

## Added

- `@consent` and `@endconsent` directives producing inert HTML templates, without evaluating visitor preferences on the server.
- `<x-consent::head />` for configuration and the embedded runtime, with CSP nonces and optional published assets.
- `window.Consent` methods for reading, choosing, accepting, rejecting, forgetting, and refreshing preferences, plus change and revocation callbacks.
- Sequential classic and module loading, including imports and top-level await, with permission checks before every script.
- Stable block IDs, duplicate prevention, shared external resource loading, and discovery of newly inserted SPA fragments.
- Default reload on active withdrawal, cancellation of pending chains, cooperative provider cleanup, and bounded loading/cleanup timeouts.
- Exact-name and prefix cookie cleanup rules scoped by path/domain, protecting preference, session, CSRF, and remember cookies.
- Strict browser validation matching PHP, same-tab temporary denial recovery after storage failures, expiry handling, and cookie synchronization across tabs and server updates.
- Script and lifecycle diagnostics, private Node/jsdom development tests, a PHP/browser serialization test, and a real-browser verification fixture.

```blade
<head>
    <x-consent::head />
</head>

@consent('analytics', 'site-analytics')
    <script src="https://your-provider.example/analytics.js"></script>
    <script>
        window.siteAnalytics.initialize({ site: 'your-site' });
    </script>
@endconsent
```

Register the analytics service in `config/consent.php`; the URL and initialization above are placeholders. Call the browser API only from an explicit choice in the application's interface:

```js
await window.Consent.choose({ analytics: true, marketing: false });
await window.Consent.rejectOptional();
```

## Changed

- Added Illuminate View as a direct dependency and exposed configurable script and cleanup timeouts.
- Service definitions can declare first-party cookie cleanup rules. Non-empty rules affect the service fingerprint; existing fingerprints remain unchanged when no rules are declared.
- `composer check` now includes JavaScript syntax and runtime tests. Node is required for development checks only, with no npm build or frontend framework needed by consuming applications.
- Documented the browser API, CSP and asset publishing, SPA behavior, withdrawal, storage failures, and the remaining milestones.

## Upgrade Notes

- Existing beta.1 cookies retain the same schema and remain valid when policy, services, and cleanup metadata are unchanged.
- Include `<x-consent::head />` in the layout before code using `window.Consent`, then wrap optional scripts in `@consent`. Scripts, pixels, iframes, and requests outside these blocks are not automatically blocked.
- Blocks support only scripts, comments, and whitespace. Blade/PHP still executes during rendering. Use explicit stable IDs for server-rendered fragments and never use the reserved `consent-auto-` prefix.
- Merge the new `loader` options into published configuration and rebuild application configuration/view caches. If serving a separate runtime file, republish `consent-assets --force` and refresh asset caches. Review overridden head views when upgrading.
- Refusal and acceptance have the same retention. A saved refusal normally reloads the page if scripts already ran; removing script elements does not disable initialized trackers. Use `onRevoke(..., { reload: false })` only for a provider that can fully stop all code in that category.
- Browser decision methods return promises. Handle storage failures in the interface. A temporary denial prevents an old grant from reappearing after a failed refusal and reload; if no fallback storage is available, the runtime reports required navigation rather than restoring the old grant.
- Cookie cleanup covers only declared, visible first-party cookies in their actual scope. Vendor APIs/server mechanisms are still needed for inaccessible cookies, other storage, and already collected data.
- This milestone includes no banner, preferences modal, English/Polish UI strings, Google Consent Mode v2, or tracker presets. Those remain in subsequent betas. It does not claim complete EU legal compliance or WCAG conformance.

See the [browser runtime guide](../browser-runtime.md) for the full API and verification instructions.
