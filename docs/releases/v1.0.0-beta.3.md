# v1.0.0-beta.3 - Accessible cookie preferences

This beta adds the cookie collection interface to the existing consent runtime. Visitors can accept all, refuse optional processing, or save a category selection from a white banner and native preferences modal. A small cookie icon makes the saved choice available again on later visits.

## Added

- `<x-consent::banner />` with a compact bottom-left or bottom-right card and a wide bottom-center layout on larger screens.
- White surfaces, light shadows, sentence case headings, spacious actions, and equally prominent acceptance and refusal.
- A native preferences dialog showing necessary plus only the optional categories used by enabled services, with their purposes and service descriptions.
- Draft category switches, explicit saving, necessary always active, reopening after acceptance/refusal, and dismissal without making a decision.
- Complete English and Polish interface strings, application-locale fallback, component overrides, and separate service-display translations that preserve the consent fingerprint.
- Validated theme colors and minimum foreground/background contrast, a configurable policy URL, and publishable styles/UI scripts.
- Keyboard operation, modal focus management, focus return, named controls, error/status announcements, reflow, text resizing/spacing support, and overlay behavior that yields to focused page controls.
- A readable fallback when JavaScript, the runtime, or native dialog support is unavailable. Without JavaScript/core, optional templates remain inert; an unsupported dialog does not override a valid saved grant.
- `data-consent-open` for custom preferences buttons and `Consent.openPreferences()` for opening the mounted interface.
- PHP-rendered UI tests, axe-core development checks, and a native-browser fixture with local mock trackers, CSP, blocked storage, and resizing/spacing controls.

```blade
<head>
    <x-consent::head />
</head>
<body>
    {{-- Your page content --}}
    <x-consent::banner />

    @consent('analytics', 'site-analytics')
        <script src="https://your-provider.example/analytics.js"></script>
    @endconsent
</body>
```

Register the analytics service and its actual purpose in `config/consent.php`. The provider URL is a placeholder. No frontend framework, Node build, database, or package decision endpoint is required.

## Changed

- Added `consent.ui` configuration for position, locale, policy link, and colors, plus Illuminate Translation as a direct dependency.
- `consent-assets` now publishes `consent.js`, `banner.js`, and `consent.css`. Both Blade components support the application's CSP nonce.
- The interface uses the existing persistence, expiry, cookie synchronization, and withdrawal lifecycle. Failed writes display an error and keep optional permission denied; rapid repeated actions do not create duplicate decisions.
- Documentation now covers the complete interface setup, service translation, customization, CSP, native browser checks, and applicable WCAG 2.2 A/AA behavior.

## Upgrade Notes

Update the package, then add the banner alongside the existing head component:

```bash
composer update webcrafts-studio/consent-for-laravel
```

This beta requires no migrations. For a local path installation, update the checkout to this tag before updating the consuming application.

Merge the new configuration into previously published config:

```php
'ui' => [
    'position' => 'bottom-left',
    'locale' => null,
    'policy_url' => '/cookies',
    'colors' => [],
],
```

Set the actual policy URL and keep the registered service descriptions accurate. `locale: null` follows Polish app locales and uses English otherwise. Choose `bottom-right` or `bottom-center` for the other positions. Override only the colors you need; inaccessible combinations are rejected before rendering.

If you use separate assets, republish and refresh your deployment's asset caches:

```bash
php artisan vendor:publish --tag=consent-assets --force
php artisan config:cache
php artisan view:clear
```

```blade
<x-consent::head :src="asset('vendor/consent/consent.js')" :nonce="$cspNonce" />
<x-consent::banner
    :style-src="asset('vendor/consent/consent.css')"
    :script-src="asset('vendor/consent/banner.js')"
    :nonce="$cspNonce"
/>
```

The application supplies the fresh nonce and matching CSP header for scripts/styles. Custom colors still emit a small inline theme style. Review overridden package views after upgrades and preserve the documented markup hooks.

- Existing beta.1/beta.2 cookies keep the same schema. Position, color, and UI language changes do not invalidate them when policy/service metadata is unchanged.
- Use `consent-translations` and `consent-views` publishing tags for customization. Add `lang/vendor/consent/pl/services.php` for translated service display; a material purpose change still requires canonical metadata or policy-version changes.
- An optional footer button with `data-consent-open` opens preferences. Closing or editing a draft does not save a decision. A saved refusal normally reloads if code already ran, using the existing runtime rules.
- The default interface targets its applicable WCAG 2.2 A and AA criteria. Published view/CSS changes and the complete host website need their own checks. This release does not claim blanket WCAG certification or complete EU legal compliance.
- Google Consent Mode v2, GA4, Google Ads, GTM, Meta Pixel, and Clarity remain subsequent milestones.

## Verification

- `composer check` passed on Laravel 13 / PHP 8.4: strict Composer validation, Pint, PHPStan, 170 PHP tests with 341 assertions, and 77 JavaScript tests.
- The PHP suite passed in four isolated installed dependency configurations: Laravel 12/13 with highest dependencies on PHP 8.3, and both majors with lowest dependencies on PHP 8.4. The older Symfony Translation emits its upstream nullable-parameter deprecation on PHP 8.4.
- All 22 interface JavaScript tests also passed with Blade rendering on Laravel 12 / PHP 8.3. The wider eight-combination matrix remains defined in GitHub Actions; local checks are separate from remote workflow results.
- Native-browser checks passed for all positions, both languages, inline/published assets under CSP, keyboard focus loops and cancellation, selection, reopening across visits, withdrawal/reload, declared cookie cleanup, and storage-error presentation.
- Both banner and all-category modal had no horizontal overflow at 320 CSS pixels, including combined 200% text size and increased text spacing. Keyboard focus scrolled the final modal action into view.
- Full native axe checks found no violations in the tested states. Closed-modal opener references and one overlapping banner text background required manual review. Actual screen readers, other engines, OS high-contrast modes, and the entire host website were not certified by these checks.
