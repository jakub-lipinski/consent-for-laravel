# v1.3.0 - Optional consent decision audit log

This release adds **optional database decision history** with **signed, immutable snapshots** of the rendered banner and preferences dialog. Explicit acceptance, refusal, preference changes, and withdrawal are linked to the wording prepared for that page, including custom translations and cached HTML. **Auditing is disabled by default**, and existing saved preferences remain compatible.

## Added

- An `audit` config section with documented enablement, database connection, table names, same-origin endpoint, independent retention, and request timeout. The optional `consent-audit-migrations` publishing tag creates the two audit tables only when the owner publishes and runs the migration.
- `consent_decisions` stores the event UUID, pseudonymous browser history identifier, referenced notice, explicit action, complete category choices, UTC server receipt time, and submitted preference expiry. UUID uniqueness deduplicates delivery retries, and conflicting reuse returns HTTP 409.
- `consent_notices` stores a unique snapshot fingerprint, policy and service versions, effective locale, and the complete snapshot. Many decisions share the same notice; changed wording creates a new notice when the next explicit decision arrives.
- Notice snapshots capture the actual rendered banner/dialog HTML, requested/effective locales, resolved translations, canonical services, presentation settings, preference lifetime, and bundled asset fingerprints. Partial/custom dictionaries, regional fallbacks, component overrides, and edits inside the published view's capture block are included.
- HMAC notice verification with `APP_KEY` and Laravel's `app.previous_keys`. Cached pages submit their original signed snapshot after text changes; the server does not rebuild historical wording from current translations.
- A signed, HttpOnly browser history cookie scoped to the audit endpoint. The audit tables store no IP address, user-agent, email, or account ID. This groups decisions from the same browser while the cookie remains available; it does not authenticate a person.
- `consent:audit-prune` removes decisions older than the configured audit retention and old notices with no remaining references. Retained decisions protect their notices through a restricting foreign key. Pruning is explicit and separate from preference-cookie validity.

## Changed

- When auditing is enabled, new optional grants wait for a matching receipt after the database transaction commits. A missing migration, invalid signature, unavailable endpoint/database, timeout, or invalid receipt prevents those grants.
- Refusal and withdrawal apply locally immediately. Mixed changes remove previous grants immediately and wait for a receipt before adding new grants. A later refusal or withdrawal supersedes a pending grant, so a delayed receipt cannot restore permission.
- Delivery begins with same-origin `fetch` keepalive before active revocation can reload the page. Transient network/server errors receive one bounded retry with the same event UUID and body. Client errors do not retry. Failures emit `consent:error` with code `audit` and reject the API promise.
- Consent reads and page rendering remain free of audit database access and identity creation. Page loads, dialog opening, expiry, and cookie edits do not create audit events. PHP cookie helpers remain unchanged; custom server interfaces explicitly supply their own signed notice and decision to the audit APIs.
- README now includes the optional feature and links to its installation, retention, customization, and failure guidance.

## Upgrade

```bash
composer require "jakub-lipinski/consent-for-laravel:^1.3.0"
php artisan view:clear
```

Commit the application's Composer files and deploy with `composer install`. Preserve existing services, presets, IDs, policy version, cookie scopes, and custom wording. Rebuild configuration/view caches and restart long-running workers.

**Existing configs work without the new section and keep auditing disabled.** Enabling audit history does not retroactively log or invalidate saved choices. The preference cookie schema, unchanged service fingerprints, and existing decision lifetimes remain compatible.

For audit history, merge this section into the application's published `config/consent.php` and select the connection/table names before migrating:

```php
'audit' => [
    'enabled' => false,
    'connection' => null,
    'decisions_table' => 'consent_decisions',
    'notices_table' => 'consent_notices',
    'path' => '/consent/decisions',
    'retention_days' => 180,
    'timeout_ms' => 5000,
],
```

```bash
php artisan vendor:publish --tag=consent-audit-migrations
php artisan migrate
```

Then set `audit.enabled` to `true` and rebuild configuration and route caches. Keep the selected connection, table names, endpoint, and cookie names stable. Auditing requires a valid `APP_KEY`, correct trusted-proxy configuration, and CSP allowing `connect-src 'self'`.

Update customized banner views with the bundled notice capture block and nonce-protected `data-consent-notice` JSON, preserving translations and control bindings. Refresh/cache-bust published `consent.js`. Inline components use the installed sources directly. This release does not change `banner.js` or `consent.css`; update them too when skipping an earlier release that changed them. Clear cached HTML when deploying the new view/runtime or changing consent purposes or signing keys.

Choose audit retention for the application's evidence requirements; **180 days is a configurable default, not a prescribed legal duration**. A null retention disables pruning. Schedule the command in the application's `routes/console.php`:

```php
use Illuminate\Support\Facades\Schedule;

Schedule::command('consent:audit-prune')->daily()->withoutOverlapping();
```

Audit events describe submitted choices at server receipt time. Cookie writes can subsequently fail, browser history can split after cookie deletion or simultaneous initial requests, and delivery is not guaranteed offline or after reload/tab closure. There is no persistent offline queue. Snapshots archive the server-prepared interface and policy link, not external policy documents or later DOM mutations. The application remains responsible for evidence access, backups, retention, and legal requirements.

See the [audit log guide](https://github.com/jakub-lipinski/consent-for-laravel/blob/v1.3.0/docs/audit-log.md) for full installation, stored fields, cached notices, key rotation, custom views/server flows, and failure behavior.

- The complete PHP suite also passed **423 tests / 2179 assertions** in an isolated PHP 8.3 / Laravel 12.69.3 dependency set. These locally executed environments are distinct from the configured eight PHP 8.3/8.4 and Laravel 12/13 lowest/highest CI combinations.
- Regressions cover signed/custom/cached notices, all seven languages and both variants, partial/regional dictionaries, published-view edits, nonce handling, key rotation, stateless reads/rendering, input/origin/size rejection, transaction rollback, duplicate/conflicting event IDs, independent retention, and pruning of unreferenced notices.
- Browser runtime tests cover receipt-gated activation, all four decision actions, retry deduplication, immediate refusal/withdrawal, mixed changes, superseded grants, failed delivery, missing notices, invalid receipts, and oversized submissions.
- A disposable native Chrome host outside the package passed **18 scenarios** covering seven languages in both variants, optional module activation after receipt, active withdrawal/reload, keyboard modality, nonce CSP, cookie isolation, original wording from cached HTML, 320px reflow, 200% text sizing, cross-origin rejection, and simulated storage failure.
- Twelve independent PHP processes submitting the same event produced one decision and one browser history identifier. Other database engines, browser engines, live tracker delivery, arbitrary custom layouts, and whole-site legal/accessibility certification are not claimed.
